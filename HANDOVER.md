## Two more real bugs found this session, both fixed

- **Balances page bounced straight back to Home on open.** `app/_layout.tsx`'s `RootStack` has a route guard (`STICKY_VOLUNTARY`) whitelisting which top-level routes it lets a signed-in user stay on (`settings`, `edit`, `reports`) — anything not in that set gets force-redirected back to `(tabs)`. The new `balances` and `shared-expenses` routes weren't in it, so navigating there immediately bounced back. Fixed by adding both to the set + registering them as `Stack.Screen` with `headerShown: false` (matching `reports`'s pattern) so they don't also get a stray native header on top of their own `ModalHeader`.
- **The app failed to open at all** (both platforms) after a full restart, following several OTA pushes in a row. Root cause found: `app/_layout.tsx` called `initDatabase()` fire-and-forget in a `useEffect`, never gating anything on it finishing — so `AuthContext`'s post-sign-in bootstrap and Home's receipt load could start querying/writing columns that the ALTER TABLE migrations hadn't added yet, on a device where migrations hadn't finished running. This was a **latent pre-existing race**, not introduced this session — it just got measurably more likely to lose the race as more migration statements piled up (three new columns landed in one session: `phone`, `phone_verified`, `paid_by`). Fixed by tracking a `dbReady` state and gating the whole app's render on it, same pattern already used for `fontsLoaded`. **Not 100% certain this was THE cause** (couldn't reproduce locally, diagnosed from user-reported symptoms + first-principles review) — if a full-app-launch failure recurs, get the actual on-screen crash text (red/white error screen with a stack trace) next time, it wasn't available this round.
- Given how much OTA churn happened rapidly this session, it's worth `eas update:list --branch preview` if anything seems to regress — every intermediate state got its own update group and can be inspected/republished individually (`eas update:republish --group <id>`) to bisect.
- **The other person's Balances screen showed "All settled up" even with a real split.** This was the flagged-but-not-yet-fixed known limitation from earlier in this doc, hit for real: `split.participantIds`/`LineItem.splitWith` stored the literal string `'self'` for whoever last saved it, and `lib/balances.ts` resolved `'self'` to whoever's CURRENTLY VIEWING — so on any device other than the one that saved the split, the real creator silently vanished from the participant set, and balances computed to zero. Fixed at the source: `app/edit/[id].tsx`'s `handleSave` and item-modal save, plus `app/(tabs)/scan.tsx`'s item-modal save, now substitute the signed-in user's REAL uid for `'self'` before persisting (mirrors how `paidBy` already worked) — both for `split.participantIds`/`split.values` keys and `LineItem.splitWith`. Load-side normalizes the reverse direction (a real uid matching the current viewer reads back as `'self'` for the UI state). **Receipts split BEFORE this fix still only resolve correctly on the original creator's device** — `resolveSelf` in `lib/balances.ts` keeps the old viewer-based fallback for backward compat, so old data isn't broken, just not retroactively fixed. Tell the user to re-toggle split (off then on) on any already-split receipt they want the other person to see correctly.
- **THE actual root cause, found via a temporary debug readout added to Settings** ("Sync status (debug)" — shows `getCloudSyncDiagnostics()`'s `lastReceiptSync` ok/fail + message, since cloud sync is otherwise 100% silent with zero user-facing error surface). The user's live device showed: `FAILED · ... · Unsupported field value: undefined`. Firestore rejects a write OUTRIGHT — the entire document, not just the offending field — if ANY field, including nested ones, is `undefined`. `Receipt.split.values` is explicitly set to `undefined` for the `'equal'` split method (the default) in `app/edit/[id].tsx`'s save — so ANY equal-split receipt's cloud write was failing completely and silently. The receipt itself (name/amount/category) still synced fine on *creation* (that write has no `split` field yet), which is why it showed up in the Expenses tab on both devices but never carried its split data across — exactly the "Test" repro. Fixed with a recursive `stripUndefinedDeep()` in `lib/cloudSync.ts`'s `serializeReceipt`, converting any `undefined` to `null` before the doc is written — a general fix, not specific to `split.values`, so any future optional field added the same way won't silently break sync again. **The debug Settings section is still in the app** (`app/settings.tsx`, "Sync status (debug)") — intentionally left in for now since this class of bug (silent sync failure) has no other way to detect; consider removing once confidence is high, or wiring `lastReceiptSync` failures to a visible toast instead.
- **After the 'self'-uid fix above, the OTHER person's phone STILL showed "All settled up."** Real bug, found by tracing the sync pipeline end to end: `app/edit/[id].tsx`'s `handleSave` spreads the OLD loaded `receipt` object into `updateReceipt(...)` without bumping `updatedAt` — so the JS object's `updatedAt` field is stale by the time it's saved. `updateReceipt` (lib/database.ts) correctly stamps a FRESH `new Date().toISOString()` for the LOCAL SQL row, but was shipping the caller's STALE `receipt.updatedAt` to Firestore via `syncReceiptToCloud(receipt, hid)`. Combine that with the earlier "skip upsert if local is already at least as fresh" guard (added to fix the rebuild-resets-split bug) and the two fixes fought each other: the OTHER household member's device would compare its own (older but still >= the incoming stale timestamp) local copy against this stale cloud write and conclude nothing needed updating — so a real, newer edit silently never propagated. Fixed by stamping ONE `now` timestamp in `updateReceipt` and using it for BOTH the local row and the object passed to `syncReceiptToCloud`. This was the actual remaining blocker — the 'self'-uid fix was necessary but not sufficient on its own.
- **Split settings reset after rebuilding.** Root cause: `lib/cloudSync.ts`'s `syncReceiptToCloud` is fire-and-forget with no retry — if the app process gets killed (e.g. for a native rebuild) right after a local save but before that write reaches Firestore, the cloud doc is left stale. `subscribeToHouseholdReceipts` does a full resync of every receipt on each fresh app launch, and `upsertReceiptFromCloud` (`lib/database.ts`) previously overwrote the local row unconditionally — so a stale cloud snapshot could silently regress a newer local edit, which is exactly what "goes away every time we build" looks like. Fixed by comparing `updated_at` before overwriting: if the local row is already at least as fresh as the incoming cloud doc, skip the upsert entirely. This is a general fix (protects against this for ANY field, not just split) — but it's a first pass at a real last-write-wins problem in this sync design; a `paidBy`/currency field could theoretically hit the same class of bug before this fix, worth keeping an eye on.

## Real bugs found and fixed in earlier sessions (patterns worth knowing before touching this code again)

- **Dark-mode contrast**: `t.colors.primary` (dark navy) is identical in both light AND dark theme — only a couple of tokens (`tabActive`) got a proper dark-mode override. Anything painted with `primary` as a bare foreground color, or as a small-control fill, is functionally invisible in dark mode. Fixed broadly (`6f61750`). **If you add a new button/chip/badge, check it in dark mode before considering it done.**
- **Currency (the deep one)**: `Receipt.totalAmount`/line-item amounts/everything numeric is USD-canonical; `formatCurrency(amountUsd, code)` converts for display only. Multiple screens have been caught reading/writing the raw USD number directly with zero currency awareness (Add Expense, Expense Detail, PDF/CSV export, and this session's Expenses-tab bug) — **any new screen showing a dollar amount must go through `formatCurrency`, never a bare `$` + raw number.**
- **`lib/cloudSync.ts`'s Firestore mirror** was missing `originalCurrency` and (until this session) `paidBy` — both now added to `serializeReceipt`/`CloudReceiptShape`/`upsertReceiptFromCloud`. Check this 3-way chain (type → serialize → deserialize) whenever a new `Receipt` field needs to survive a sync round-trip; it's easy to add a field to `types/index.ts` and the local DB and forget the cloud path.
- **Safe-area / notch**: screens that set `headerShown: false` and roll their own header must wrap in `<SafeAreaView edges={['top']}>` themselves.
- **expo-router tab-param stickiness**: a query param set once on a tab route stays set forever across refocuses unless explicitly cleared with `router.setParams({ mode: undefined })`.
- **In-app camera** (`expo-camera`) and **push notifications** (`expo-notifications`) were both native-dependency additions in an earlier session — same rebuild caveat as this session's `expo-contacts`.
